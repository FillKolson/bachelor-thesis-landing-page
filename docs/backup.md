# Резервне копіювання проєкту

## Стратегія резервного копіювання

- DNS-статичний сайт: конфіг + артефакти збірки + вихідний код
- Якщо є база даних на бекенді: регулярні dump

## Типи резервних копій

- Повні: `tar` всіх файлів + `pg_dump` всіх БД
- Інкрементальні: `rsync --link-dest`
- Диференціальні: `rsync` проти останнього повного

## Частота створення

- Статичної частини: раз на день або при релізі
- База даних: кожні 1-4 години в залежності від SLA

## Зберігання та ротація

- Локальна папка `/backups` + S3/глобальне сховище
- Ротація: за 14/30/90 днів

## Процедура резервного копіювання

1. Код + артефакти:
   - `tar czf /backups/project-code-$(date +%F).tar.gz /var/www/project`
2. Конфіг:
   - `tar czf /backups/project-config-$(date +%F).tar.gz /etc/nginx/sites-available/your.conf`.
3. Дані користувача:
   - `rsync -a /path/to/user-data /backups/user-data-$(date +%F)`
4. Логи:
   - `logrotate` + архівування в `/backups/logs`

## Перевірка цілісності

- `sha256sum` файлів у backup та підтвердження
- Періодичне тестове відновлення в staging

## Автоматизація (скрипти)

- `scripts/backup.sh` (bash)
- cron наприклад `0 2 * * * /usr/local/bin/scripts/backup.sh`

## Відновлення

### Повне відновлення

1. Розпакувати archive з кодом
2. Налаштувати nginx / середовище
3. Встановити залежності `npm ci`
4. Запуск `npm run build` і `npm run preview`

### Вибіркове відновлення

- файли: один конфіг, один статичний ресурс
- БД: `pg_restore`/`mysql < dump.sql`

### Тестування відновлення

- Виконати restore на staging і перевірити UI + інструменти

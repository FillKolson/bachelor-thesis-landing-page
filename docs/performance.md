# Профілювання та оптимізація продуктивності

## Ціль

Визначити ділянки застосунку, що споживають найбільше ресурсів (CPU/пам’ять/рендер), зафіксувати базові метрики, знайти щонайменше 3 “гарячі точки”, виконати оптимізації та підтвердити покращення повторним профілюванням.

Проєкт: **Vite + React** (SPA/landing).

## Інструменти профілювання

### CPU / UI Rendering (браузер)

- **Chrome DevTools → Performance**: запис трасування, flame chart, main thread time, scripting/rendering/painting.
- **React DevTools → Profiler**: тривалість commit’ів, “why did this render”, компоненти з найбільшим вкладом у рендер.
- **Performance API (`performance.now`)**: локальні вимірювання в сценаріях `#/perf`.

### Пам’ять (браузер)

- **Chrome DevTools → Memory**:
  - Heap snapshot (пошук утримуваних об’єктів, витоків),
  - Allocation instrumentation on timeline (алокації під час сценарію),
  - Перевірка росту heap після багаторазового запуску сценарію.

### I/O (localStorage) та мережа

- **Chrome DevTools → Performance/Network**:
  - витрати на `localStorage` (часті `JSON.stringify/parse`, синхронні записи),
  - Network (для цього лендінгу запитів майже немає; фокус — UI та localStorage).

> Профілювання БД не застосовується: у цьому репозиторії немає коду запитів до БД.

## Ключові метрики для цього проєкту

- **CPU (ms)**: час виконання сценарію (локально) + Main thread time (DevTools Performance).
- **UI rendering (ms)**: commit duration у React Profiler + кількість ререндерів.
- **I/O (localStorage)**: кількість/частота записів, час на `JSON.stringify/parse`.
- **Пам’ять**: зміна Heap (до/після), наявність “залипання” об’єктів після повторів.

## Тестові сценарії та набори даних

Додано технічну сторінку **`#/perf`** (`src/pages/PerformancePage.jsx`) — вона створює відтворювані навантаження:

1. **CPU: sort + reduce**
   - Дані: 50 000 об’єктів (штучний датасет)
   - Операції: `Array.sort` + цикл з акумуляцією
   - Мета: отримати стабільний CPU профіль на main thread.

2. **Logger: 2000 records**
   - Дані: 2000 лог-записів `INFO`
   - Мета: виміряти overhead логера та I/O в `localStorage`.

3. **Render: list**
   - Дані: список `N` елементів (керовано інпутом, напр. 2 000 / 10 000 / 20 000)
   - Мета: профілювання React commit’ів і DOM оновлень.

Рекомендовані режими даних (додаткове завдання “різні набори даних”):

- **Малий**: list size 500
- **Середній**: list size 2 000
- **Великий**: list size 10 000–20 000

## Методологія проведення

1. Запустити dev-сервер: `npm run dev`.
2. Відкрити `#/perf`.
3. Для кожного сценарію:
   - Записати **локальний час** (відображається на сторінці),
   - Паралельно записати трейс у **DevTools Performance** (Start profiling → Run scenario → Stop),
   - Для рендер-сценарію — додатково запис у **React Profiler**.
4. Повторити кожен сценарій 3–5 разів і брати медіану (щоб згладити “шум”).

## Виявлені “гарячі точки” (база)

Нижче — проблемні місця, які дають найбільший вклад при сценарії **Logger: 2000 records**:

1. **`src/logger/logger.js`: синхронні записи в `localStorage` на кожен лог**
   - Симптом: високе навантаження CPU + блокування main thread.
   - Причина: `JSON.stringify` великого масиву + `localStorage.setItem` у кожному `logRecord`.

2. **`src/logger/logger.js`: `JSON.parse`/читання буфера на кожен лог**
   - Симптом: зайвий CPU.
   - Причина: початково буфер перечитувався з `localStorage` при кожному записі.

3. **`src/logger/logger.js`: отримання `userId/sessionId` через storage на кожен лог**
   - Симптом: додаткові синхронні I/O операції.
   - Причина: `getOrCreateStorageId` звертався до `localStorage/sessionStorage` щоразу.

## Реалізовані оптимізації

Оптимізації виконані в `src/logger/logger.js`:

- **Кешування буфера логів у пам’яті** (`bufferCache`) замість `readLogBuffer()` на кожен запис.
- **Debounce запису в `localStorage`** (типово 250ms) замість синхронного запису кожного разу.
- **Кешування `anonUserId` та `sessionId`** в модулі після першого отримання.
- **Flush на `visibilitychange(hidden)` та `beforeunload`** (best-effort), щоб мінімізувати втрату логів.

## Нові “гарячі точки” після оптимізацій

Після того, як overhead логера зменшено, новими кандидатами зазвичай стають:

- рендер великого списку (DOM/React commit),
- сортування великих масивів,
- інші синхронні операції main thread.
